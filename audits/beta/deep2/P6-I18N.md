## 1. The merge chain, from code, before any count

The brief requires this first, and it is the reason two previous counts were
wrong. Read from source, not assumed:

| file:line | what it does |
|---|---|
| `shared/utils/mergeLocales.js:11` | `export function mergeLocales(shared, portal)` |
| `admin/src/i18n.js:4-6` | imports `sharedEn/sharedUz/sharedRu` from `shared/locales/*.json` |
| `admin/src/i18n.js:11-15` | `resources = { uz: { translation: mergeLocales(sharedUz, portalUz) }, … }` |
| `reception/src/i18n.js:11-15` | same shape |
| `government/src/i18n.js:11-15` | same shape |
| `teacher/src/i18n.js:18-20` | `const uz = mergeLocales(sharedUz, portalUz)` |
| `teacher/src/i18n.js:59-62` | `resources = { uz: { translation: mergeDeep(uz, uzParent) }, … }` — **three catalogues** |

So the catalogue a portal actually resolves against is:

```
admin | reception | government   shared/locales/<L>.json  +  <portal>/src/locales/<L>/common.json
teacher (and parent)             shared  +  teacher/src/locales  +  teacher/src/parent/locales
```

**`shared/locales/*.json` (138 keys per locale) was never loaded by the gate this
campaign inherited.** Correcting that drops the English-fallback count from **57
to 47** — ten were keys that existed in `shared/` all along.

This is the third time an incomplete catalogue has produced a wrong number here:
Campaign I first reported **214** raw keys (missed the parent catalogue; real
answer 8), then **57** fallbacks (missed `shared/`; real answer 47). Each time the
error was over-reporting, and each time it was caught by checking the claim
against something already known.

## 3. D-58 — one portal fell back to the wrong language

```
teacher      fallbackLng: 'uz'
admin        fallbackLng: 'en'      <-
reception    fallbackLng: 'uz'
government   fallbackLng: 'uz'
```

`admin/src/i18n.js:30` alone fell back to English. In a product whose users are
Uzbek school directors, a missing key in the admin portal degraded to English
while the same missing key in any other portal degraded to Uzbek. Changed to
`'uz'` for consistency with the other three.

This is the kind of thing a completeness matrix does not show — the matrix is
about what exists, and this is about what happens when something does not.

## 6. Per L6 — what this green is blind to

`0 raw keys` means no `t('…')` call site fails to resolve. It does **not** mean:

- **that hardcoded strings are covered.** D-40 (`Show N errors`, `DOB:`,
  `Gender:`, `Class:`) and D-45 (the government CSV header) are English literals
  that never enter i18n at all. No catalogue check can see them, and both are
  still open.
- **that the translations are correct.** `backend/i18n/README.md` and the
  `_note` keys both say the translations are AI-generated and unverified. The
  gate proves a key resolves, not that it resolves to the right words.
- **that interpolation is right.** `{{count}}` plural forms are counted as
  present whether or not the plural rule matches the language — Russian has three
  plural forms and the catalogue carries `children` / `children_plural`, a
  two-form English shape.
- **that a key rendered is a key seen.** The renders cover five pages. A raw key
  on a modal, an error toast or a rarely-hit branch would not appear.

The third point is the most likely to bite: Russian plurals under a two-form
scheme will render "2 детей" style errors that no gate here detects.
